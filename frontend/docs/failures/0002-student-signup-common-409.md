# 0002. Student signup step 3 showed 「잠시 후 다시 시도」 for COMMON_409

## Date Observed

2026-10-05

## Failure Type

Runtime failure (user-visible), cross-environment mismatch suspected.

## Goal

「회원가입 완료」 on student signup step 3 should either succeed or tell the
user what to fix. A fully empty certificate row must never reach
`POST /auth/student`.

## What Happened Or Was Tried

Browser test: a certificate row added with 「+ 자격증 추가」 was left empty and
「회원가입 완료」 was pressed. `POST /auth/student` returned 409
`{"error":{"code":"COMMON_409","message":"이미 존재하는 데이터와 충돌합니다."}}`
and the screen showed only 「잠시 후 다시 시도해 주세요」. Without that row the
same signup returned 200. The request payload was not captured.

## Why It Failed

- User-visible error: `COMMON_409` and `COMMON_400` fall through to the
  generic 「잠시 후 다시 시도해 주세요」, but retrying the same input fails
  again, so the user had no way out.
- Root cause of the 409 is not confirmed, but it is not the certificate row:
  - The tester left both certificate fields blank. The frontend drops such
    rows, so both the failing and the succeeding request carried
    `certificates: []`; the two requests had the same body.
  - `COMMON_409` is the backend's handler for any
    `DataIntegrityViolationException`. `student_certificates` has no unique
    constraint, and a blank certificate would have been a 400.
  - The same body failing once and then passing fits an identity sequence
    behind its table: if rows were inserted with explicit ids (the specialty
    seed was added to the DB outside the Flyway migrations), the next
    `GENERATED BY DEFAULT AS IDENTITY` value can hit an existing id. The
    failed insert still uses up that value, so the retry gets a free id.
    Signup inserts into `student_profiles`, `student_specialties`, and
    `refresh_tokens`, so one of their sequences is the likely suspect.

## Current Replacement

- `isBlankCertificate` decides which rows are left out, and
  `certificateStatuses` blocks partly filled rows, out-of-range years, and
  duplicate names (spaces and case ignored) before sending (ADR 0019).
- `registerStudentSignup` maps any other 400 to `invalidInput`
  (「입력한 내용을 다시 확인해 주세요」) and any other 409 to `dataConflict`
  (「일시적인 문제가 생겼어요. 다시 시도해도 안 되면 문의해 주세요」).
  「잠시 후 다시 시도해 주세요」 is only for 5xx and network errors. Clear 409s
  (`STUDENT_409_NUMBER`, `USER_409_EMAIL`, `USER_409_REGISTERED`) keep their
  own messages.
- A first fix showed `COMMON_409` as 「입력한 내용 중 이미 있는 정보가 있어요」;
  it was replaced because this 409 was not about the input.

## Detection Or Prevention Check

Manual review point (no frontend test runner yet): when adding a submit error,
check that a 400 which fails again with the same input does not map to
「잠시 후 다시 시도」, and that `COMMON_409` does not ask the user to fix the
input. When a signup fails, capture the request payload from the
Network tab. For `COMMON_409`, the backend should compare each signup table's
`max(id)` with its identity sequence (`pg_get_serial_sequence`) on that DB,
and read the constraint name from the server log.

## Agent Guidance

- Do not tell the user to fix the input for `COMMON_409`; it can come from
  server data. A plain 400 does fail again with the same input, so it keeps
  the check-your-input message.
- `COMMON_409` hides which constraint failed; ask the backend to log or narrow
  it rather than guessing in the frontend.
